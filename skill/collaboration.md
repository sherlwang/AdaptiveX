# 大模型协作与工具提炼案例

以下记录来自本项目的材料整理和工程验证过程。引号内为实际对话节选，其余为处理摘要。案例不附原始私有 RTL 或完整聊天附件，工程与工具的测试结果分别记录。

## 1. 从原始赛题纠正目录安排

### 1.1 实际问题与提示词

整理材料时，工程与 Skill 放在外层两个目录，模型又将 GitHub 上传范围限定为工程。这个选择没有清楚说明 Skill 的比赛提交要求，用户提出：

> 诶 你看下赛题的pdf 我怎么记得skill这些也要提交。

### 1.2 回答与纠正

模型重新读取自主选题的提交章节后回答：

> 你记得对，Skill 明确要提交。我刚才把它排除在 GitHub 之外，是目录安排上的选择，不是赛题要求。

核对结果为：§3.3.3.1 要求技能包随作品提交；§3.3.5.2 要求 `skill/` 和 README，说明适用范围、用法、失效条件、效果及提炼来源；§3.3.5.4 的推荐仓库布局也包含 Skill。网页又为视频、报告、代码压缩件和 GitHub 链接设置了不同入口，因此不能把网站上传件与仓库维护目录当成一件事。

总目录将工程、原生 Vitis 工作区与 Skill 分别维护。报告、视频与签字授权书按网站入口另交；代码压缩件从同版工程源输入与必要依赖提取。GitHub 的公开范围及大文件方式由最终发布选择确定。

### 1.3 沉淀与边界

先核对正式要求，再定义公开文件选择；目录选择本身不构成赛题要求。该经验用于 `sherl-github-project-publish` 的显式文件选择和上传检查。验证范围是提交内容及目录关系，不代表获得赛务合规认定。

## 2. Vitis 不能只验证能够打开

### 2.1 实际需求

用户确认：

> vitis_new这个文件可以提交 应该是代码包和工程包都要。

原工作区包含有效应用源码，也包含旧硬件、旧平台及机器路径。最初的方案是把它整理成可导入的 IDE 工程。实际检查发现，能够导入和读取平台，并不能证明换目录后可编译。

### 2.2 处理与自我纠正摘要

1. 对照应用文件，确认两端各 21 份源码及链接文件与交付源码一致。
2. 对照硬件导出，避免沿用旧工作区的 XSA 与 bit；采用对应工程原样导出的两端 XSA。
3. 在新目录尝试原生导入、重新生成 BSP 和切换引用平台，发现旧绝对引用或新的 BSP 库搜索路径仍可能导致失败。
4. 工具提示构建结束时，继续检查实际 ELF。出现链接失败且无 ELF 的尝试没有计为通过。
5. 收敛为源码、匹配 XSA 和原有 `build_app.tcl`：在新目录创建平台、BSP 与应用，再编译并检查真实 ELF。

### 2.3 实际验证

| 角色 | 应用配置 | 结果 |
|:---|:---|:---|
| Tx | A53 standalone 64-bit，`RFDC_PROFILE=0` | 新工作区产出实际 ELF，返回码 0 |
| Rx | A53 standalone 64-bit，`RFDC_PROFILE=1` | 新工作区产出实际 ELF，返回码 0 |

源码、XSA、内含 bit 与 ELF 的绑定记录见[PS 交付复核](../AdaptiveX_Prj/results/software/handoff.json)，实际入口见[板级软件说明](../AdaptiveX_Prj/software/board/README.md)。本项为新工作区的软件构建验证。最终交付另在根目录提供原样 `vitis_workspace/`；其本轮核对范围为复制一致性，分别记录两种入口的验证状态。

### 2.4 沉淀与边界

源依赖核对需要沿平台、硬件导出、应用源码和实际输出逐项确认。工程交付检查不能停在窗口能打开或工具打印成功。该经验用于 `sherl-vivado-source-audit` 的依赖审查和 `sherl-vivado-netlist-delivery` 的输入、产物绑定。

## 3. 文件在目录里不等于会被上传

### 3.1 实际要求

用户要求：

> 提交的工程的代码和后面要压缩的代码包需要是一样的。

模型为此核对工程文件、发布选择和 Git 忽略规则。发现原规则 `*.xsa` 会把新增的两份有效硬件定义排除；仅检查文件清单完整，仍不足以说明 Git 会收录它们。

### 3.2 纠正与验证

为两份指定 XSA 增加精确例外，同时保留对其他运行产物的忽略。随后在本地临时 Git 环境中，对照应发布文件与 Git 实际选择，检查字节是否受自动换行转换影响。

前一工程目录阶段的检查覆盖 383 项应发布文件，实际选择全部匹配。最终目录新增完成态 Tx/Rx 工程和原生 Vitis 工作区，需要按最终文件选择再次核对。工程完整交付、代码 RAR 和 GitHub 选择分别定义，报告、视频、签字件及生成的压缩件按比赛入口提交。

最终代码 RAR 从同版工程源输入、必要依赖及 Skill 提取，逐项核对对应文件哈希，不纳入完成态运行目录与 IDE 缓存。生成真正的 RAR 后，解压复核所选文件与工程中的对应内容。

### 3.3 沉淀与边界

`sherl-github-project-publish` 固化显式选择、哈希检查、暂存字节核对及有授权后才推送的流程。文件选择通过不证明算法正确，也不替代作者决定公开范围和许可证；通信正确性仍由工程测试记录说明。
